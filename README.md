# symphony-protocol

The claim protocol for pull-request-gated Claude agents, as one Python package with no dependencies. Workers, a person's sessions, routines on Claude accounts and runs in GitHub Actions alike, share a repository by claiming an issue as a branch `claude/<issue>`, working in the open on a draft pull request, and landing only what merges cleanly with the default branch as it is now. This package holds those rules once, so every place that runs them gives the same answers: the board that shows who holds what and which open work meets in a file, the coordinator that releases idle claims and tells overlapping work, the registry of workers, the check that holds a pull request to the protocol, the clerk, the push guard, and the merge gate. The protocol in prose is [spec/PROTOCOL.md](spec/PROTOCOL.md). It needs Python 3.12 or later and its standard library, nothing else.

## What is in it

| Module | What it holds |
| --- | --- |
| `sdlc_protocol.labels` | The labels the protocol reads and writes, with their colours, and a worker's label `worker:<name>`, read under its older spellings `account:` and `agent:` too. |
| `sdlc_protocol.claims` | The claim branch's name, the claim file `docs/agents/claims/<n>.md` and how to read it, which claims are due for release, what a release comment is, and the name `released/<n>-<sha>` a released claim's branch takes. |
| `sdlc_protocol.board` | The board, STATE.md, rendered from a Snapshot of the repository, with the files more than one piece of open work changes and the order that work should land in, the comments it is due to post ("main moved", idle), and which claims the coordinator released, whose issues go back to the queue. |
| `sdlc_protocol.coordinator` | The coordinator's rules, run in the board's own run: which claims to release and the comment that releases each (why, whose, what the branch holds, the plan), and what to tell open work that meets other work in a file. |
| `sdlc_protocol.workers` | The registry of workers, one JSON file per worker under `.github/symphony/workers/`: what a file may say, the check of a folder of them, which paths an area takes, and the answers of the "Add a worker" issue form. |
| `sdlc_protocol.protocol_check` | The problems a `claude/<issue>` pull request has against the protocol, for CI to fail on. |
| `sdlc_protocol.team` | The clerk: seeding an epic's tasks onto the registered workers, routing the coordinator, telling each worker what to do next, with the shared work dealt by area. |
| `sdlc_protocol.guard` | The push guard's rules: which `git push` commands a session may not run. |
| `sdlc_protocol.gate` | The merge gate: the protocol's decisions as a Policy over a World. |
| `sdlc_protocol.adapters` | The worlds: `github` (the REST API), `bare_git` (a shared bare repository), `memory` (tests and simulations). |
| `sdlc_protocol.vendoring` | The record `VENDORED` a vendored copy carries (version, commit, a sha256 per file) and the check a consumer runs on its copy; it imports nothing from the package, so it runs as a script inside any copy. |
| `sdlc_protocol.cli` | `python3 -m sdlc_protocol <board, check, team, workers, guard or verify-vendored>`, a thin shell over the modules above. |

The rules are plain functions and dataclasses over what they are handed, and the clock is an argument. Only `adapters/` calls GitHub or changes a git repository, and `cli.py` reads the environment and the event; the two other places that look outside are small and named: `guard.branches` asks the local git which branch is checked out, and `board.write_if_changed` writes STATE.md. That is what lets the same rules run in a GitHub workflow, in a benchmark's hub and in a test.

Beside the package, [validation/](validation/README.md) holds the design of a harness that validates these rules against the spec, with the findings it turned up, and the prototype that design measured; nothing there is part of the package, vendored into a consumer or run by the test suite.

## The four consumers

Four repositories run a copy of the package in their own tree, and [ecosystem.json](ecosystem.json) is the one record of who takes what: each consumer's repository, where its copy lives, which modules it takes, what it uses them for and the check it runs. [ECOSYSTEM.md](ECOSYSTEM.md) draws that record and the package's imports as a map, generated by `python3 scripts/architecture.py`; `bash scripts/check.sh` fails while the map is out of date.

The template repository, OpenSpineConsortium/symphony-template, takes the whole package under `tools/sdlc_protocol`, so its workflows and its Claude Code hooks need nothing but `python3`. Its board workflow (with the coordinator's step in it), its CI's protocol check and registry check, the coordinator's and the workers' workflows and the PreToolUse hook on Bash run the board, the check, the clerk, the registry and the guard through its shims tools/board.py, check_protocol.py, team.py, workers.py and guard_push.py, which hand their arguments to `python3 -m sdlc_protocol board`, `check`, `team`, `workers` and `guard`.

Coordbench, the benchmark that compares ways of coordinating agents, takes the whole package under `coordbench/vendor/sdlc_protocol` and imports `sdlc_protocol.gate` and `sdlc_protocol.adapters.bare_git` for its sdlc arm: the agents share a bare repository, and the arm's hub claims, opens and lands pull requests through the gate, under a policy in which the gate itself merges. An experimental way of gating is another Policy behind the same interface, kept in coordbench, not here.

The plugin marketplace, OpenSpineConsortium/symphony-marketplace, takes only `guard.py` under `plugins/sdlc/vendor/sdlc_protocol`, for the push guard in its plugin's PreToolUse hook; the guard imports nothing but the standard library. It also names its plugin's manifest, `plugins/sdlc/.claude-plugin/plugin.json`, as its version file, whose version the sync raises with each new copy (Vendoring, below).

The GitHub App, OpenSpineConsortium/symphony-app, takes `claims.py` and `protocol_check.py` under `app/vendor/sdlc_protocol`, and posts `protocol_check.problems_for` on every pull request as the check run `sdlc/protocol`. `sdlc_protocol.adapters.github` (`GitHub(token, repo)` with an installation token, and `GitHubWorld(api, policy)` as the world the gate reads and merges through) is here for the day the App also answers with the gate's decisions.

Every copy also takes `__init__.py`, which states the version, and `vendoring.py`, the check of the copy against its record. Every consumer's copy is changed only by the sync's pull request (below), never by hand.

## The policy

`gate.Policy` is how the protocol behaves where it runs, and the world, below, is where it runs; the rules themselves are the same everywhere. `claim_prefix` is what a claim branch starts with (`claude/`). `required_check` is the check that must be green before the gate merges (`check`, or empty where merging cleanly is the whole check). `bring_main_in` is how a branch takes in a default branch that has moved: `rebase`, a session's way, with the one `--force-with-lease` the protocol allows, or `merge`, a worker in Actions', so nobody force-pushes. `who_merges` is who moves the default branch: `owner` by hand, `gate` when a pull request is marked ready, or `auto-merge` once the required check is green. `idle_after` is how long a claim may go without a commit before it is released (24 hours). `remote` and `default_branch` are only the names the gate's answers use. `gate.ACCOUNT_POLICY` (rebase, the owner merges) and `gate.TEAM_POLICY` (merge, auto-merge) are the two ways of landing the spec describes.

## The world

`gate.World` is where the branches live, as the gate needs to see them, and an adapter implements it. `main_sha()` and `branch_sha(branch)` give commits, or "" when there is none. `standing(branch)` says how a branch stands to the default branch: `clean`, `behind`, `conflicting` or `unknown`. `check(branch)` gives the required check's state on the branch's head: `green`, `red`, `pending` or `none`. `merge(branch)` lands the branch and returns a `MergeResult` with the default branch's new commit, or raises `MainMoved` (the default branch is left as it was), `MergeRefused`, `GateFailed` or, where the policy leaves merging to someone else, `NotAllowed`. `now()` is the world's clock. The GitHub world reads the standing from the pull request's mergeable state and the check from the head's check runs, and merges through the merge API only when `who_merges` is `gate`; the bare-git world asks git itself and names the conflicting files, runs no checks and merges with `git merge --no-ff`, pushed without force; the memory world takes standings and checks set by hand and a clock that moves only when told. The gate's refusals exit with codes a script can tell apart: 1 refused, 2 someone else's, 3 main moved, 4 gate failed.

## The command line

Each subcommand takes the arguments the template's own tool for the job took, so a workflow line changes only in what it runs. These are the template's workflow lines, rewritten:

```
python3 -m sdlc_protocol board --default-branch "$DEFAULT_BRANCH" --sha "$(git rev-parse HEAD)" --out "$RUNNER_TEMP/STATE.md"
python3 -m sdlc_protocol check
python3 -m sdlc_protocol team route --event "$EVENT" --issue "$ISSUE" --label "$LABEL"
python3 -m sdlc_protocol team seed --epic "$EPIC" --plan "$RUNNER_TEMP/plan.json" --registry .github/symphony/workers
python3 -m sdlc_protocol team next --agent "$WORKER" --registry .github/symphony/workers --label "worker:$WORKER"
python3 -m sdlc_protocol workers check
python3 -m sdlc_protocol workers list --runs actions
python3 -m sdlc_protocol workers from-form --body "$RUNNER_TEMP/issue.md"
python3 -m sdlc_protocol guard < payload.json
```

`board` and `team` call GitHub with `GITHUB_TOKEN` on the repository in `GITHUB_REPOSITORY` (`team --repo OWNER/NAME` names another). Before it renders, `board` runs the coordinator: it releases each claim gone a day without a commit, comment first, then the labels, and tells each piece of open work about other work it meets in a file; then it renames the branch of each released claim to `released/<n>-<sha>`, which takes a token that may write the repository's contents, says once on the issue which rulesets stand in the way when GitHub refuses a rename, and posts the comments that are due, all unless given `--render-only`; `board --dry-run tests/fixtures/board.json` renders a saved snapshot with no network at all. `check` reads the pull request from the event in `GITHUB_EVENT_PATH`. `team` takes the workers from the registry folder `--registry` names: `seed` gives tasks to every registered worker, and `next` deals the shared work among the workers in Actions, each by its area; without it, from `CLAUDE_TEAM`, a JSON list such as `["w1","w2"]`, as team mode did. `team schema --registry DIR` prints, with no network, the JSON schema the coordinator's plan answers to, a task's owner one of the registered workers. `workers` reads the registry offline: `check` holds every file to its rules, `list` gives the names as a JSON list for a workflow's matrix, `describe` a line per worker for the coordinator's prompt, `get` one setting, and `from-form` writes the worker an "Add a worker" issue's answers describe and prints its name and how it runs. `guard` reads the hook's JSON on stdin and exits 2, with the reason on stderr, to refuse a push. `verify-vendored VENDOR_DIR` holds the copy `VENDOR_DIR/sdlc_protocol` to its record `VENDOR_DIR/VENDORED`, as `vendoring.py verify` does (below). A vendored copy is not installed, so it runs by its path, as in `python3 tools/sdlc_protocol verify-vendored tools` from the template's root, or with its directory on the path, `PYTHONPATH=tools python3 -m sdlc_protocol verify-vendored tools`; a bare `python3 -m sdlc_protocol` there finds no module.

## Running the tests

From the repository's root, with Python 3.12, the oldest version the package supports:

```
python3.12 -m unittest discover -s tests -v     # the whole suite
python3.12 -m unittest tests.test_gate -v       # one module's tests
bash scripts/check.sh                           # what CI runs
```

`tests/test_parity.py` holds the package to the template's own tools, byte for byte, on the inputs the template's tests use; it reads a clone of symphony-template beside this repository (or one still named sdlc-template, from before the rename), or the one `SDLC_TEMPLATE` names, and skips when there is none, as on CI. Since the template vendored the package, its tools are shims over the copy, so the test reads them from the template's git as they stood before that commit.

`scripts/check.sh` first holds every file to ASCII with LF endings and a final newline, since the package is vendored into repositories whose own checks demand that, then holds ECOSYSTEM.md to what `python3 scripts/architecture.py` would write, then runs the whole suite. CI (`.github/workflows/ci.yml`) runs it on Python 3.12 as the job named `check`, and runs each consumer's own check on this change as the jobs `downstream (<consumer>)`.

## Vendoring

```
python3 scripts/vendor.py <consumer checkout> [--consumer OWNER/NAME]
scripts/vendor.sh <target repository> [--consumer OWNER/NAME]
```

`scripts/vendor.py` finds the consumer in ecosystem.json by `--consumer`, or else by the checkout's `git remote get-url origin`, and fails with the list of consumers when neither names one. It replaces `<vendor_dir>/sdlc_protocol` with the files that consumer takes, without Python's caches, so a module removed here is removed there too; it refuses a copy whose modules import one the copy would leave out, and refuses to vendor into this repository. Then it writes `<vendor_dir>/VENDORED`:

```
sdlc-protocol <version> <commit>
<sha256>  <path inside the copy>
...
```

one line per copied file, sorted by path, in the layout `sha256sum` writes. The version is read from `sdlc_protocol/__init__.py` without importing the package. The commit is the last commit that changed `sdlc_protocol/`, not HEAD, so a merge commit on main records the same commit its pull request's branch did and a change elsewhere here brings no new copy; it ends in `-dirty` when the package has changes not yet committed, and is `unknown` outside a git checkout, so the record never names a commit the copy does not match. A second run changes nothing and says so. Where ecosystem.json names a `version_file` for the consumer, a run that changes the copy's files also raises that file's patch version, `0.1.0` to `0.1.1`, and leaves every other byte of it alone: Claude Code keeps an installed plugin on its cached copy until the version in the plugin's manifest changes, so a new guard with no new version would land in the marketplace and reach no session. A run that leaves the copy's files as they were leaves the version alone, even when the record names a newer commit, and a version file that is missing or states no `MAJOR.MINOR.PATCH` version refuses the run before anything is written. Nothing in the target is committed: that is the target's own pull request. `scripts/vendor.sh` runs the same command; it stays for old checkouts and for hands that still type it, while the consumers' documents name `scripts/vendor.py`.

A consumer's own check holds its copy to the record, offline, before its tests:

```
python3 <vendor_dir>/sdlc_protocol/vendoring.py verify <vendor_dir>
```

prints one line, `vendored sdlc-protocol <version> at <short commit>: <n> files match VENDORED`, and exits 0, or names each problem and exits 1: the record missing, or in the old one-line format, which asks for a re-vendor; a recorded file missing; a file edited by hand ("change it in sdlc-protocol and let the sync bring it"); a file in the copy that the record does not list. Python's caches never count.

## How a change reaches the other repositories

One push to main does it; nobody copies anything by hand.

1. A pull request here runs `check`, this repository's own suite, and `downstream (<consumer>)` for each consumer in ecosystem.json: the job checks out the consumer's main beside this checkout, vendors this change into it with `scripts/vendor.py`, and runs the consumer's own check there. A change that would break a consumer is red here, before it merges. A public consumer is read with the run's own token, which reaches no other repository that is not public; an internal or private one (the template is internal, the App private) only with the App's token, minted to read that one repository, when `SDLC_APP_ID` is set and the pull request is not from a fork, and its leg otherwise says it skipped.
2. The owner merges it.
3. The push to main starts `.github/workflows/sync.yml` (also run by hand, and weekly as a fallback; a run by hand from any branch but main vendors nothing and says so). For each consumer it vendors main into a checkout of that consumer and, when anything changed, commits as the App's bot on the branch `symphony-protocol/sync`, which belongs to the workflow alone and is force-pushed, then opens the pull request from it or updates the one already open. It pushes only when the copy differs from what that branch already holds, so a run with nothing new does not restart the consumer's CI, and it takes as its own only a pull request whose branch is in the consumer itself, never one from a fork whose branch has the same name. The body says what changed in the library since the commit the consumer's record named, which files of the copy were added, changed or removed, and what the consumer uses the library for. On the plugin marketplace the same commit raises the plugin's version whenever the copy's files change, and the body says so, so the pull request is also the plugin's release: once it merges, the sessions that have the plugin installed take the new guard at their next plugin update, by themselves where the marketplace's auto-update is on. The App's token is scoped to that one consumer and to contents and pull requests, and a push made with it starts the consumer's CI, which one made with `GITHUB_TOKEN` would not. Where the consumer's main already holds the copy, the sync closes its pull request still open there, with a comment saying why.
4. The consumer's own check decides; `vendoring.py verify` is part of it.
5. Where ecosystem.json gives the consumer `auto_merge`, which it gives all four, the sync arms auto-merge with GitHub's `enablePullRequestAutoMerge`, which never merges by itself, so the pull request lands once the required check is green. It does not use `gh pr merge --auto`, which merges at once a pull request GitHub does not count as blocked, before the consumer's check has run. Where GitHub refuses to arm it (auto-merge not allowed in the repository's settings, or no check required on its main, so nothing to wait for), the run's summary and its log give GitHub's reason and the pull request waits for its owner. symphony-app is private, and GitHub offers auto-merge on a private repository only on a paid plan, which its organization has; on GitHub Free the same refusal is reported and its owner merges.

The run's summary has a row per consumer: up to date, the stale pull request closed, or the pull request opened, updated or already holding this copy, and whether auto-merge is armed. Only one sync runs at a time, and a newer push waits for it rather than cancelling it. The logic the workflows call is `scripts/sync.py` (the matrix of consumers, the title, the commit message, the body, the closing comment, the summary), where it is tested; the workflow files only run git, gh and that script, and every value reaches a shell step through `env:`, never an expression inside `run:`.

### A change a consumer must answer

Some changes are meant to change what a consumer sees: a rendered string that a consumer's test pins (the template's tests compare the board with tests/fixtures/board-STATE.md), or a function a consumer calls differently. That consumer's `downstream (<consumer>)` job is red on such a change, as it should be, and the sync cannot carry it: it rebuilds `symphony-protocol/sync` from the consumer's main on every run and force-pushes it, so a fix pushed to that branch is lost at the next run. The consumer goes first:

1. Open the pull request here; its `downstream (<consumer>)` job shows which consumer the change breaks, and how.
2. In that consumer, open a pull request of its own that vendors this branch and answers the change: from a checkout of this pull request's branch, `python3 scripts/vendor.py <consumer checkout>`, then the consumer's test or code updated to match, in the same pull request. Its check passes, since the copy matches its record and the test reads the new output.
3. Merge the consumer's pull request first. Then re-run this pull request's `downstream` jobs, which vendor the same branch into the consumer's new main and pass, and merge this one with a merge commit, so the commit the consumer's record names stays the last one that changed the package.
4. The sync then finds that consumer up to date, and closes any sync pull request still open there, since main already holds the copy. After a squash merge instead, it brings the record's new commit line, and nothing else.


## The owner's one-time setup for the sync

Until the variable `SDLC_APP_ID` is set here, the sync skips itself, stays green and says in the run's summary what is missing. To set it up, once:

1. Install the GitHub App Symphony (OpenSpineConsortium/symphony-app) on all five repositories, or on all of the organization's repositories.
2. On this repository, set the App's id as the variable `SDLC_APP_ID` and its private key as the secret `SDLC_APP_PRIVATE_KEY`, the same values symphony-template has. Run these from a clone of OpenSpineConsortium/symphony-app, whose .sdlc-app.env `scripts/register.py` wrote, so the key goes through a pipe and never onto the screen:

   ```
   gh variable set SDLC_APP_ID --repo OpenSpineConsortium/symphony-protocol --body 5258276
   python3 scripts/register.py --print-key | gh secret set SDLC_APP_PRIVATE_KEY --repo OpenSpineConsortium/symphony-protocol
   ```

   A key downloaded by hand from the App's settings goes in with `< path/to/key.pem` in place of the pipe.

3. Allow auto-merge on the consumers ecosystem.json gives `auto_merge`:

   ```
   gh api -X PATCH repos/OpenSpineConsortium/symphony-template -F allow_auto_merge=true
   gh api -X PATCH repos/OpenSpineConsortium/coordbench -F allow_auto_merge=true
   gh api -X PATCH repos/OpenSpineConsortium/symphony-marketplace -F allow_auto_merge=true
   gh api -X PATCH repos/OpenSpineConsortium/symphony-app -F allow_auto_merge=true
   ```

4. Require the check `check` on each consumer's main, with a ruleset, so auto-merge waits for it to be green; the sync only arms auto-merge, and GitHub refuses to arm it on a pull request with nothing left to wait for, which the run's summary then reports. On this repository require `check` and, if you like, the `downstream (<consumer>)` jobs.

## Releases

A release is the version in `sdlc_protocol/__init__.py` and `pyproject.toml`, raised together by the pull request that changes what the package does. Nobody tags it by hand: once the version reaches main, `.github/workflows/release.yml` tags the first commit of main's first-parent line that carries it, the pull request's merge, as `v<version>`, and publishes the GitHub release with GitHub's own notes on what merged since the last one. `scripts/release.py` says what to tag: every version back to the newest one already tagged, oldest first, so a release a failed run or a burst of merges left untagged is made by the next run, and a tag that exists is never moved. The run needs only its own `GITHUB_TOKEN`; it also runs by hand, and a run by hand from any branch but main tags nothing.

## Installing

A consumer that would rather install than vendor can: `pip install "sdlc-protocol @ git+https://github.com/OpenSpineConsortium/symphony-protocol@<tag>"` builds the package from a release tag, with no dependencies to fetch. The wheel carries the spec as `sdlc_protocol/spec/PROTOCOL.md`, read with `importlib.resources.files("sdlc_protocol") / "spec" / "PROTOCOL.md"`; a vendored copy does not, since the repository it lands in keeps its own copy of the protocol.
